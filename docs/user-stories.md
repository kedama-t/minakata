# Minakata ユーザーストーリー仕様

## 1. 概要

### 1.1 プロダクトの目的

Minakata は、エージェントベースの自動情報収集とチーム共有ナレッジベースを統合したツールである。エージェントが Web を継続的に調査し、調査結果を Markdown ベースの Wiki 形式で蓄積する。チームメンバーは WebUI から閲覧・検索・レビューでき、深掘りしたい内容は対話エージェントに依頼することで追加調査を発火させられる。

### 1.2 提供する価値

- **情報収集の自動化と省力化**: 設定したトピックについて、エージェントが毎晩自動で Web を調べて記事化する。チームは「朝、開いたら昨夜分の調査結果が読める」状態を得る
- **チーム共有のナレッジベース**: 一人が依頼した調査結果がチーム全員の資産になる。重複調査を避け、レビューで品質を担保する
- **継続的に追跡される情報**: 一度作った記事はエージェントが鮮度チェックして自動更新を続ける。古くなった情報はアーカイブされる
- **対話による深掘り**: チャット UI または記事コメント経由で、自然言語で追加調査を依頼できる

### 1.3 想定ユースケース

- 「生成 AI の最新情報、フレームワーク、新サービス、新モデルのリリースなどを自動収集したい」
- 「特定のフレームワークやツールの情報を継続的に追いかけたい」
- 「過去にチーム内で調査した内容を、対話形式で引き出したい」

### 1.4 想定スコープ規模

- 同時利用ユーザー: 〜10 名(チーム単位)
- 記事数: 〜10,000
- 1 日あたり調査タスク: 〜500

## 2. ペルソナとロール

ロールは 3 段(技術スタック仕様 セクション 6)。

| ロール     | 主な操作                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| **Viewer** | 記事の閲覧・検索のみ。チャット利用不可、依頼不可                                                        |
| **Editor** | Viewer の操作に加え、調査依頼・チャット・レビュー(承認/差し戻し)が可能                                  |
| **Admin**  | Editor の操作に加え、ユーザー管理・破壊的操作の承認(アーカイブ/大幅書き換え/エージェント自己改善)が可能 |

## 3. ドメイン用語の前提

以下の概念を本書全体で前提とする。

| 用語                                   | 意味                                                                                                           |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **記事 (Article)**                     | 1 つのトピックに対応する Markdown ファイル。`frontmatter` でメタデータを保持                                   |
| **トピック (Topic)**                   | 記事の主題。記事に紐づく検索キーワード群と概念領域                                                             |
| **調査タスク (Research Task)**         | キューに積まれる調査の単位。新規作成・追記・鮮度チェックなどの種類がある                                       |
| **対話セッション (Chat Session)**      | チャット UI における 1 つの会話単位                                                                            |
| **メッセージ (Message)**               | 対話セッション内のユーザー発言またはエージェント応答                                                           |
| **レビュー (Review)**                  | 記事に対するチームメンバーの承認/差し戻し操作                                                                  |
| **リサーチ方針 (Research Policy)**     | チーム共通の調査ルール。優先ソース、粒度、出典必須要件、執筆フォーマット等を定義                               |
| **購読 (Subscription)**                | 定期調査の対象トピック登録。デイリーリサーチで自動消化される                                                   |
| **対話エージェント (Dialogue Agent)**  | ユーザーと直接対話するエージェント。Hermes の `dialogue` subagent                                              |
| **調査エージェント (Research Agent)**  | 調査キューを消化し記事を編集するエージェント。Hermes の `researcher` subagent                                  |
| **鮮度チェッカー (Freshness Checker)** | 記事の最終更新からの経過時間に基づき再調査タスクを投入するエージェント。Hermes の `freshness_checker` subagent |
| **ChangeLog 日報**                     | 調査エージェントが前日の活動をまとめた記事。日付別に作成される                                                 |

## 4. ユーザーストーリー

### 4.1 認証・チームアクセス

#### US-1.1: 初期セットアップ

**As a** Minakata を導入したいエンジニア  
**I want to** Docker Compose を 1 つ実行するだけで Minakata 一式を起動したい  
**So that** 環境構築に時間を使いたくない

**シナリオ**:

1. ユーザーが Git リポジトリを clone
2. `.env` に必要な API キー(`MCP_TOKEN`, `OPENCODE_API_KEY`, `FIRECRAWL_API_KEY`, `SEARXNG_SECRET`)を設定
3. `docker compose up -d` を実行
4. ブラウザで `http://localhost:3000` を開く
5. 初回アクセス時に管理者アカウント作成画面が表示される
6. 管理者のメール・パスワードを設定して登録完了

**受け入れ条件**:

- [ ] `docker compose up` 1 コマンドで全サービス(minakata / hermes / searxng)が起動する
- [ ] 起動時に SQLite スキーマ・FTS5・sqlite-vec の初期化が自動実行される
- [ ] 埋め込みモデル(`multilingual-e5-base`)が初回起動時にダウンロードされ、`./models` にキャッシュされる
- [ ] 初回起動時のみ管理者作成画面が表示され、2 回目以降はログイン画面に遷移する
- [ ] セットアップに必要な手順は README に明記

**関連技術コンポーネント**: 技術スタック §5.9 デプロイメント

---

#### US-1.2: メンバー招待

**As a** Admin  
**I want to** チームメンバーを Minakata に招待したい  
**So that** チーム全員で同じナレッジベースを使えるようにする

**シナリオ**:

1. Admin が設定画面の「メンバー管理」を開く
2. 招待したい相手のメールアドレスとロール(Viewer / Editor / Admin)を入力
3. 招待リンクを発行する
4. 招待された人がリンクを開き、パスワードを設定してアカウント有効化
5. ログイン後、自分のロールに応じた画面が見える

**受け入れ条件**:

- [ ] 招待リンクには有効期限がある(デフォルト 7 日)
- [ ] 招待リンクは 1 度使うと無効になる
- [ ] パスワードは Argon2id でハッシュ化されて保存される
- [ ] ロールは後から Admin が変更できる
- [ ] メンバーが自分でアカウントを新規作成することはできない(招待ベース)

**関連技術コンポーネント**: 技術スタック §5.2 認証、§6 認証・認可

---

#### US-1.3: ログインとセッション

**As a** チームメンバー  
**I want to** 一度ログインしたら一定期間は再ログイン不要にしたい

**受け入れ条件**:

- [ ] ログイン後のセッションは Cookie ベース(JWT)で保持される
- [ ] セッション有効期限は 30 日(設定で変更可能)
- [ ] ログアウト時は Cookie がクリアされる
- [ ] 別端末からのログインも可能(セッション数の制限なし)

### 4.2 デイリーリサーチ(購読型)

#### US-2.1: 購読トピックとリサーチ方針の設定

**As a** Editor  
**I want to** リサーチしたいトピックと、その調査方法を設定画面で指示したい  
**So that** 毎晩、自分(またはチーム)が知りたい情報を自動的に集めてもらえる

**シナリオ**:

1. ユーザーが「購読設定」画面を開く
2. 「+ 新規トピックを追加」をクリック
3. トピック名(例: 「LLM エージェントの最新動向」)、調査範囲(キーワード、優先ソース、除外条件)、粒度(浅い概要 / 深堀り)、出力フォーマット指定 等を入力
4. 保存すると、次回の夜間バッチから自動調査が始まる

**受け入れ条件**:

- [ ] 1 トピックには複数のキーワードと優先ソース URL を指定可能
- [ ] 「ニュース・リリースだけ」「論文・技術文書も含む」等の調査深度を選べる
- [ ] チーム共通の「リサーチ方針」(出典必須・粒度・執筆スタイル等)とは別に、トピック個別の指示も書ける
- [ ] 設定変更は次回バッチから反映、過去記事は遡及変更しない

**関連技術コンポーネント**: 技術スタック §5.8 タスクキュー(scheduled 優先度)

---

#### US-2.2: 夜間バッチによる自動調査

**As a** Editor  
**I want to** 朝までに昨日購読したトピックの調査が完了していてほしい  
**So that** 始業時にその日のキャッチアップができる

**シナリオ**:

1. 03:00(設定で変更可)に Hermes の `daily_research` subagent が起動
2. アクティブな購読トピックを順に `minakata.enqueue_task(type="daily_research", ...)` でキューに投入
3. `researcher` subagent がキューを消化、各トピックについて Web 検索・抽出・記事化を実行
4. 既存記事がある場合は追記、新規トピックは新規作成
5. 朝 7:00 までに完了することを目標

**受け入れ条件**:

- [ ] バッチ起動時刻は Hermes の自然言語 cron で「毎日午前 3 時に...」と記述可能
- [ ] 各タスクには優先度 `scheduled` が付与される(対話起点の `urgent` / `interactive` より低い)
- [ ] 失敗したタスクは指数バックオフで最大 3 回リトライ、なお失敗なら DLQ に隔離
- [ ] 朝までに完了しないトピックがあった場合、ダッシュボードで遅延が可視化される
- [ ] LLM コスト・Web 抽出クレジット消費が記事 frontmatter に記録される

**関連技術コンポーネント**: 技術スタック §5.4 エージェントハーネス、§5.6 Web 検索・抽出、§5.8 キュー

---

#### US-2.3: 朝の閲覧

**As a** Editor  
**I want to** 朝、Minakata を開いて昨夜の調査結果を一望したい

**シナリオ**:

1. ユーザーがログイン
2. トップ画面に「昨夜更新された記事」一覧と「新規作成された記事」一覧が表示される
3. 各記事の更新差分のサマリ(2-3 文)が一緒に出る
4. 興味のある記事をクリックして本文を読む

**受け入れ条件**:

- [ ] 「昨夜の更新」は最新の調査エージェント実行サイクル(例: 直近 24 時間)を基準
- [ ] 差分サマリは記事更新時にエージェントが生成し、frontmatter に保存
- [ ] 既読/未読の状態は個人ごとに管理される
- [ ] 大量更新時もスクロールでスムーズに見られる UI(ページング or 仮想スクロール)

---

#### US-2.4: ChangeLog 日報の自動生成

**As a** Editor  
**I want to** 調査エージェントが昨日何をしたかを 1 ページで把握したい  
**So that** 「全体として何が動いているか」を確認できる

**シナリオ**:

1. 調査エージェントが次回の調査サイクル開始前(または前サイクル終了直後)に、前回サイクルの活動をまとめる
2. ChangeLog 専用の記事(`changelog/2026-05-21.md` のような日付別ページ)に書き込む
3. 内容: 新規作成された記事一覧、更新された記事一覧、各記事への追記要約、失敗したタスク、コスト集計
4. ChangeLog はタグ `changelog` で検索可能

**受け入れ条件**:

- [ ] ChangeLog 自体も通常の記事として保存される(同じデータモデル)
- [ ] サイクルごとに 1 ページ(夜間バッチなら日次)
- [ ] エージェント起因の自動生成記事であることが frontmatter に明示される(`source: agent_changelog`)
- [ ] ChangeLog からリンクされる記事は記事 ID で参照、リネーム耐性を持つ

### 4.3 個別調査(対話・コメント起点)

#### US-3.1: チャット UI からの調査依頼

**As a** Editor  
**I want to** チャットインターフェイスで「○○について調べて」と依頼したい  
**So that** 興味を持ったその場で深掘りができる

**シナリオ**:

1. ユーザーが対話チャット画面を開く
2. 「React Router v7 の framework mode について調べて」と入力して送信
3. 対話エージェントが内容を解釈し、調査キューに追加
4. ユーザーには「調査タスクを追加しました(完了見込み: 約 3 分)」のような応答が返る
5. 完了したら通知が出る、または対話の続きとして「調査が完了しました。記事はこちらです」と返ってくる

**受け入れ条件**:

- [ ] チャットメッセージは `core.MessageService.post()` で SQLite に保存される
- [ ] Hermes が 30 秒以内にメッセージをポーリングして応答開始する
- [ ] 応答はストリーミング(SSE)でブラウザに表示される
- [ ] 対話エージェントは「追加タスク化が必要」と判断したら `minakata.enqueue_task(priority="urgent", ...)` を呼ぶ
- [ ] urgent タスクは 5 分以内に処理開始される

**関連技術コンポーネント**: 技術スタック §5.2 チャット UI、§5.8 メッセージバス

---

#### US-3.2: 記事コメントからの追加調査依頼

**As a** Editor  
**I want to** 記事を読みながら「ここをもう少し詳しく」とコメントできる  
**So that** 文脈を保ったまま深掘りを依頼できる

**シナリオ**:

1. ユーザーが記事を読んでいる
2. 特定のセクション(または行)に対して「コメントを追加」を選択
3. 「この部分のセキュリティ的な懸念について調べてほしい」のような自然言語で依頼を書く
4. 対話エージェントがコメントを受け取り、対象記事への追記タスクとしてキューに投入
5. 調査エージェントが対象部分の文脈を読み込んだ上で追記を実行
6. ユーザーは記事側で追記の差分を確認できる

**受け入れ条件**:

- [ ] コメントは記事のセクションまたは行に紐づく
- [ ] エージェントが追記する場合、追記範囲(どのセクションに何を足したか)が差分として残る
- [ ] コメント自体は記事のメタデータとして frontmatter または別ファイルに保存
- [ ] 解決済みコメントは折りたためる

---

#### US-3.3: リサーチ方針との照合

**As a** チーム全体  
**I want to** 誰が依頼しても同じ品質・粒度の記事が出来上がるようにしたい  
**So that** チーム共有ナレッジとしての一貫性を保つ

**シナリオ**:

1. ユーザーが個別調査を依頼
2. 調査エージェントはまずチーム共通の「リサーチ方針」設定を読む
3. 方針に従って、調査粒度・優先ソース・必須項目(出典、関連リンク、TL;DR セクション等)を満たす形で記事を執筆
4. 方針逸脱しそうな場合はメッセージで確認する

**受け入れ条件**:

- [ ] リサーチ方針は Admin が設定画面で編集可能(Markdown で記述)
- [ ] 方針は Hermes のサブエージェントのプロンプトに毎回挿入される
- [ ] 方針が更新されても過去記事は自動書き換えされない(明示的に reindex 指示が必要)
- [ ] 方針に必須項目(例: 「全記事に出典セクションが必要」)を書ける

### 4.4 ナレッジ質問チャット

#### US-4.1: ナレッジベースへの質問

**As a** Editor  
**I want to** 蓄積された記事に対して対話形式で質問したい  
**So that** 過去に調査した内容を素早く引き出せる

**シナリオ**:

1. ユーザーが「ナレッジ質問」チャット画面を開く
2. 「先月調べた RAG の評価指標についてもう一度教えて」と質問
3. 対話エージェントが `minakata.fulltext_search` および `similar_articles`(ベクトル類似)で関連記事を検索
4. 検索結果を統合して回答、引用元の記事リンクを併記
5. 必要に応じて追質問できる

**受け入れ条件**:

- [ ] 回答には引用元の記事リンクと該当箇所が明示される
- [ ] 関連記事が見つからない場合、エージェントが「ナレッジベースには見当たりません」と正直に答える
- [ ] 質問への回答はストリーミング表示される

**関連技術コンポーネント**: 技術スタック §5.1 EmbeddingService、SearchService

---

#### US-4.2: 対話中の自動深掘り判断

**As a** Editor  
**I want to** ユーザーが明示しなくても、「これは追加調査が必要」と対話エージェントが判断したら自動でキューに積んでほしい  
**So that** ナレッジの空白が自然に埋まる

**シナリオ**:

1. ユーザーが「最近の長文文脈モデルの動向は?」と質問
2. 対話エージェントが該当記事を返答するが、最新情報が 2 週間以上前であることに気づく
3. 「鮮度が落ちているので追加調査します」とユーザーに通知し、`minakata.enqueue_task(type="refresh", priority="interactive")` を呼ぶ
4. 後ほど更新が完了したら、ユーザーに完了通知

**受け入れ条件**:

- [ ] 対話エージェントは「鮮度低下」「カバレッジ不足」「矛盾」を検出する手がかりを持つ(プロンプトで定義)
- [ ] 自動キュー投入は対話相手に必ず通知する(無音で動かない)
- [ ] 同一トピックの重複投入は冪等性キー `(topic_hash, date)` で抑制

### 4.5 記事の閲覧と検索

#### US-5.1: 全文検索

**As a** Viewer 以上  
**I want to** キーワードで記事を横断検索したい

**受け入れ条件**:

- [ ] FTS5 ベースの全文検索が利用可能
- [ ] 検索結果はスニペット(該当箇所抜粋)を表示
- [ ] タグ・更新日時・ステータス(draft/published/archived)でフィルタ可能
- [ ] アーカイブ済み記事もデフォルトで検索対象、UI でオフ可能

**関連技術コンポーネント**: 技術スタック §5.1 SearchService

---

#### US-5.2: タグとカテゴリでの絞り込み

**As a** Viewer 以上  
**I want to** タグで関連記事を絞り込みたい

**受け入れ条件**:

- [ ] 調査エージェントが記事作成時に適切なタグを自動付与
- [ ] タグは frontmatter に格納(配列)
- [ ] タグ一覧から記事を絞り込める
- [ ] タグの正規化(エイリアス、表記揺れ統合)が可能

---

#### US-5.3: 類似記事の探索

**As a** Editor  
**I want to** いま見ている記事に似たトピックの記事を発見したい  
**So that** 既存ナレッジから関連情報を見落とさない

**受け入れ条件**:

- [ ] 記事ページに「関連記事」セクションが自動表示される
- [ ] ベクトル類似度(`sqlite-vec`)で計算
- [ ] 関連度の上位 5-10 件を表示
- [ ] アーカイブ済みも含まれるがその旨明示

### 4.6 レビュー

#### US-6.1: 差分レビュー

**As a** Editor  
**I want to** エージェントが書いた記事を GitHub のような差分表示で確認したい

**シナリオ**:

1. 記事が更新されると、レビュー待ち状態に入るものがある(変更規模・記事ステータスに応じて自動判定)
2. レビュー者は更新差分を行単位で確認できる
3. 各行に対してコメントを書ける
4. 「承認」または「差し戻し(コメント付き)」を選べる

**受け入れ条件**:

- [ ] 差分表示は `diff2html` 相当の見た目
- [ ] 行コメントが可能
- [ ] レビュー履歴(誰が何時に承認/差し戻したか)が記録される
- [ ] 差し戻しコメントは対話エージェントが解釈し、修正タスクをキューに積む

**関連技術コンポーネント**: 技術スタック §5.2 差分表示

---

#### US-6.2: 大幅変更時の承認フロー

**As a** チーム  
**I want to** エージェントによる記事の大幅書き換えには、誰かの承認を必要としたい  
**So that** 暴走や情報の質劣化を防げる

**シナリオ**:

1. 調査エージェントが既存記事を 30% 以上書き換える編集を提案
2. 直接反映せず、`pending_approval` 状態で保留
3. Editor 以上にレビュー通知が飛ぶ
4. 承認すると本記事に反映、差し戻しなら破棄
5. 反映前の状態が常に source of truth として残る

**受け入れ条件**:

- [ ] 変更率は文字数 diff で計測
- [ ] アーカイブ・削除は admin 承認、それ以外の大幅変更は editor 承認
- [ ] 承認待ち期間中も他のタスクは止めない(別記事は影響なく処理)
- [ ] 承認/差し戻しは監査ログに記録

**関連技術コンポーネント**: 技術スタック §6 承認ゲート

---

#### US-6.3: レビューを受けた再調査

**As a** Editor  
**I want to** 「ここの情報源が古い」「この部分は事実誤認」と差し戻したら、エージェントが直してくれるようにしたい

**シナリオ**:

1. レビュー者が差し戻し(コメント付き)
2. 対話エージェントが差し戻し内容を解釈
3. 修正用の調査タスクをキューに投入
4. 調査エージェントが該当箇所を再調査して修正
5. 再度レビュー待ちに入る

**受け入れ条件**:

- [ ] 差し戻しからキュー投入までは自動
- [ ] 修正タスクは元のレビュー対象記事と紐付く(`parent_review_id`)
- [ ] 何度差し戻されたかの履歴が残る
- [ ] 一定回数(例: 3 回)を超えてもレビュー通過しない場合、Admin に通知

---

### 4.7 鮮度管理とアーカイブ

#### US-7.1: 自動鮮度チェック

**As a** チーム  
**I want to** 一度作った記事もエージェントが定期的に最新化してほしい  
**So that** 情報が陳腐化しない

**シナリオ**:

1. 鮮度チェッカーが 6 時間ごとに動作
2. 各記事の `last_researched_at` をチェック
3. しきい値超過(1 日、3 日、1 週間、2 週間、1 ヶ月)で鮮度ランクが変わる
4. ランクに応じた優先度で再調査タスクを投入

**受け入れ条件**:

- [ ] しきい値とアクション(再調査/通知のみ/無視)はリサーチ方針で設定可能
- [ ] 鮮度ランクは記事一覧画面で色やバッジで可視化
- [ ] 再調査時、変更がなければ「変更なし」と判断して `last_researched_at` のみ更新
- [ ] 重複投入は冪等性キーで抑制

**関連技術コンポーネント**: 技術スタック §5.4 freshness_checker subagent

---

#### US-7.2: 自動アーカイブ

**As a** チーム  
**I want to** 1 ヶ月誰も触っていない記事はメンテ対象外にして、エージェントのコストを節約したい

**シナリオ**:

1. 鮮度チェッカーが「最終アクセス(閲覧・編集・コメント)から 1 ヶ月超過」を検出
2. 記事を `archived` ステータスに変更
3. アーカイブされた記事は検索・閲覧は可能だが、エージェントは自動更新の対象外
4. アーカイブ前にチームに通知(オプション)

**受け入れ条件**:

- [ ] アーカイブ判定は最終更新ではなく最終アクセスベース
- [ ] アーカイブされた記事は frontmatter で明示(`status: archived`, `archived_at`)
- [ ] アーカイブ操作も監査ログに記録
- [ ] アーカイブ可能数の上限・除外タグ等はリサーチ方針で制御可能

---

#### US-7.3: アーカイブ解除

**As a** Editor  
**I want to** アーカイブされた記事を必要になったら復活させたい

**シナリオ**:

1. ユーザーがアーカイブ済み記事を開く
2. 「アーカイブ解除」ボタンが表示される
3. クリックすると `status: published` に戻り、エージェントの自動メンテ対象に復帰
4. 復帰直後に鮮度チェッカーが優先的に再調査タスクを投入

**受け入れ条件**:

- [ ] 解除権限は Editor 以上
- [ ] 解除時、過去の調査履歴はそのまま残る
- [ ] 解除後の最初の再調査は `urgent` 相当の優先度

---

### 4.8 エージェントの自己改善

#### US-8.1: スキル提案

**As a** Hermes Agent  
**I want to** 繰り返し発生するタスクを抽象化してスキル化したい  
**So that** 次回以降の効率と品質が上がる

**シナリオ**:

1. Hermes が複数回の類似タスクを検出
2. 「このパターンをスキル化したい」と Admin に通知(WebUI の Admin ダッシュボードに表示)
3. 提案内容: スキル名、目的、生成されたスキルコード/プロンプト
4. Admin がコード差分をレビュー
5. 承認するとスキルが有効化される

**受け入れ条件**:

- [ ] スキル提案は通知だけで、自動有効化はされない
- [ ] スキル定義は `hermes-skills/` 配下にファイルとして書かれる(agentskills.io 標準。実行時 `hermes/skills/` へは起動時に seed)
- [ ] 承認時にも git コミットされ、変更履歴が残る
- [ ] 提案の却下も理由付きで記録される

**関連技術コンポーネント**: 技術スタック §5.4 スキル自動生成、§6 承認ゲート

---

#### US-8.2: スキルの無効化・削除

**As a** Admin  
**I want to** 不要になったスキルを削除したい

**受け入れ条件**:

- [ ] 削除前に「過去どのタスクで使われたか」が確認できる
- [ ] 削除も監査ログに記録
- [ ] 削除されたスキルは git の履歴から復元可能

---

#### US-8.3: 読者フィードバックによる執筆の自己改善

**As a** 読者(viewer / editor / admin)  
**I want to** 役に立った記事に「いいね」を付けたい。そしてエージェントがその傾向を学び、より評価される記事を書くようになってほしい

**受け入れ条件**:

- [ ] 記事ページから「いいね」をトグルで付け外しできる(viewer も可)。記事一覧・インサイト画面でいいね数が見える
- [ ] いいねはユーザーが WebUI からのみ付ける(P6)。エージェントはいいねを付与・操作できない
- [ ] エージェント(feedback_analyst)が、いいね/コメントの集計シグナルといいね上位/未いいね記事を読み比べ、執筆インサイト(Markdown)を更新する
- [ ] 執筆系エージェント(researcher / daily_research / changelog_writer / synthesizer)は記事執筆前に執筆インサイトを参照し、構成・粒度・文体に反映する
- [ ] 執筆インサイトは WebUI で閲覧でき、editor が手で修正できる。インサイトの更新は監査ログに残る
- [ ] チャット・コメントのテキストフィードバックと合わせ、3 チャネルがエージェントの自己改善ループを形成する

## 5. 横断的な要件

### 5.1 出典管理

すべての記事は出典を持つ。

**要件**:

- 記事 frontmatter の `sources` フィールドに `{ url, fetched_at, archive_url?, used_in_sections[] }` を必ず格納
- 引用箇所と出典の対応関係を保持
- リサーチ方針で「全記事に出典セクションが必要」を強制可能
- 出典のリンク切れは鮮度チェッカーが検出して通知

### 5.2 監査

すべての変更系操作は監査ログに残る(技術スタック §7)。

**最低限の記録項目**:

- いつ・誰が(actor)・どのエージェントで(agent_name)・どのツールで(tool_name)・何を(target_article_id)・どう変えたか(before_hash, after_hash)・なぜ(source_request_id)・いくら(cost_usd)

### 5.3 セキュリティ

技術スタック §8 に従う。

**ユーザーストーリー視点での要点**:

- ユーザーがエージェントに指示する経路は WebUI のみ(P6)
- 外部メッセージング・ゲートウェイなし(Telegram/Discord 等)
- Web 取得テキストは untrusted データとして扱われ、エージェント命令には変換されない
- 破壊的操作には承認ゲートが必須

### 5.4 プライバシー

- 記事本文は外部 API に送信されない(埋め込みはローカル、P11)
- 外部送信が発生するのは: (a) 生成 LLM へのプロンプト、(b) Web 検索クエリ、(c) Web 抽出対象 URL のみ
- 個人特定情報を含む可能性のある内容に対しては、リサーチ方針で「外部送信前に編集」を指定可能

---

## 6. スコープ外(本書では扱わない)

| 項目                                                     | 理由                                            |
| -------------------------------------------------------- | ----------------------------------------------- |
| 外部メッセージング(Telegram / Discord / Slack)からの操作 | 入口は WebUI のみ(P6)                           |
| リアルタイム共同編集                                     | 人間は記事を直接編集しない(P5)                  |
| ブラウザ自動化が必要なログイン後のサイト調査             | 初期は `web_extract` のみ。必要になったら追加   |
| 動画・音声コンテンツの取り込み                           | 初期はテキストのみ                              |
| モバイル専用アプリ                                       | レスポンシブ Web で十分とする                   |
| 多言語 UI                                                | 日本語と英語の混在記事は扱うが、UI は日本語固定 |
| GDPR / SOC2 等のコンプライアンス                         | チーム内自己ホストを想定、外部公開しない        |

## 7. 受け入れテスト(MVP)

初版リリースの完了判定として、以下の通しシナリオが動くこと。

**シナリオ 7.1: チーム導入から朝の閲覧まで**

1. Admin が `docker compose up -d` で起動
2. 管理者アカウント作成、Editor を 2 名招待
3. Editor A が「Bun の最新リリース」をデイリーリサーチに登録

5. ChangeLog 日報が存在することを確認

**シナリオ 7.2: 対話からの個別調査**

1. Editor A がチャットで「React Router v7 framework mode について調べて」と依頼
2. 5 分以内に新規記事が作成される
3. 記事に出典が含まれる
4. 記事に適切なタグが付与されている

**シナリオ 7.3: レビューと差し戻し**

1. Editor B が既存記事に大幅追記をエージェントに依頼
2. 30% 超の変更が `pending_approval` 状態になる
3. Editor A が差し戻し(コメント付き)
4. エージェントが修正タスクを実行
5. 再度レビュー待ちに戻り、承認すれば反映

**シナリオ 7.4: 鮮度チェックとアーカイブ**

1. 10 記事程度を蓄積した状態
2. ナレッジ質問チャットで複合的な質問
